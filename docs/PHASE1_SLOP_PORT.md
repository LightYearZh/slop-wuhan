# 下一步：武汉数据接入 Slop New York 原运行时

本文件描述下一迭代的技术任务，不声称已经实现。

## 路线

1. 保持 Slop New York 原版的 Three.js WebGPURenderer/TSL、角色、相机、车辆渲染和天气模块。
2. 从 `tools/convert_osm.py` 的武汉输出建立城市运行时地理格式适配层，而不是直接将纽约专属 `geo-streets.mjs` 套到武汉数据上。
3. 统一 1 米单位、东向 x、南向 z、局部 WGS84 原点。整理与 Slop 上游项目的坐标轴差异。
4. 先切换地形、道路、建筑和水域，禁止手工生成虚构武汉道路来掩盖转换问题。
5. 将 `highway=pedestrian` / `footway` / `path` 和通车道路分开。道路单行、桥梁/隧道层级未核验时先不开放驾驶。
6. 恢复步行相机、第三人称角色和车辆资产；此时车辆可以在开放的试验道路自由驾驶，不引入网约车任务。
7. 使用固定四组镜头（江汉路/沿江大道/建筑近景/俯瞰）对照 GIS 地图核对位置与比例。建立截图回归。
8. 记录性能：FPS、渲染批次数、建筑数量、每帧 CPU/GPU 时间（可获得时）。

## 阶段验收

- 数据可重建，来源、日期、坐标、估算属性记录在文档。
- 江汉路及邻接道路与 OSM 几何对应，没有整体坐标偏移。
- 建筑只有确有轮廓时才宣称基于 OSM，缺失建筑单独标记程序占位。
- 水体轮廓和沿江大道的位置关系合理；不得用一条直线冒充长江真实岸线。
- WebGPU 漫游稳定；普通道路可按设定速度驾车探索。
- 仍无打车业务逻辑；伦敦相关模块留到第二阶段。

## 优先解决的数据缺口

1. 江/湖等 OSM relation 内环、缺失水体、岸线和岛屿。
2. 重要建筑被 OSM 漏采时的 Overture 补全与去重。
3. 高度数据来源、异常值和程序化占位的区分。
4. 真实 DEM 与道路桥隧高差。
5. 道路连通性与行车方向，特别是 `layer`, `bridge`, `tunnel`, `oneway` 与禁行区。
